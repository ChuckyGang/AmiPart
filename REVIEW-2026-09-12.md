## 2. Executive summary

The engine layer (RDB core, FFS/PFS3/SFS grow and shrink) is careful work:
endian-explicit RDB access, write-back verification, tail-free gates, rollback
in the SFS/PFS engines, chain-cycle detection, and a fuzz harness that has
already caught real bugs. The defects below cluster in four places: the
partition-move I/O helper, host-only endianness in the SFS bitmap helpers, the
GUI's deferred FFS grow commit, and a handful of fixed-size string buffers.

Top items, in the order I would fix them:

1. **F-1 (CRITICAL)** Partition move and zero address blocks past 4 GB at
   `offset mod 4 GB` — the TD64 high offset word goes into the wrong field.
2. **F-2 (CRITICAL, Linux build only)** SFS grow/shrink/shrinkinfo read and
   write bitmap bits through native little-endian longword loads; the Linux
   binary writes scrambled SFS bitmaps. The fuzz harness cannot see it because
   it never compares bitmap contents. Confirmed by a differential test.
3. **F-3 (MAJOR)** `ADDPART BLOCKSIZE=1024..32768` (CLI and script) sets
   `DE_SIZEBLOCK` to a non-512 value, which makes the partition physically
   occupy `blocksize/512` times its cylinder span, and no overlap check
   accounts for that.
4. **F-4 (MAJOR)** GUI FFS grow relocates the root but defers the RDB write to
   the user's next Write; a Discard afterwards leaves a volume that looks empty
   after reboot.
5. **F-5 (MAJOR)** PR #9 is a real bug: `PartClone_PartToPart` passes a
   4-argument progress callback where the FFS/SFS grow engines call a
   2-argument one. Merge it, and stop suppressing that warning class.
6. **F-6 (MAJOR)** Two window-title buffers overflow with long image paths.

Recommendation on the open PRs: merge #8, #9 and #11 as they are; merge #7 with
one macro fix; #10 is harmless but its rationale does not match the custom
formatter (details in section 6).

## 3. Findings

Format per finding: file:line, category, what, failure scenario, fix,
confidence. Severity: CRITICAL = data loss or crash on a disk-writing path;
MAJOR = wrong result, crash or corruption on a realistic path; MEDIUM;

### CRITICAL

#### F-1 TD64 high offset written to `iotd_Count` instead of `io_Actual`
- File: `src/partmove.c:62-63`, `src/partmove.c:95-96` (used by `PART_Move` and `PART_Zero`)
- Category: data-safety
- What: `move_read_blocks`/`move_write_blocks` put the upper 32 bits of the
  byte offset in `iotd_Count` and set `io_Actual = 0`. The TD64 convention,
  `BlockDev_ReadBlock` (`src/rdb.c:598-600`), and the host shim
  (`host/amiga_shim.c:489-491`) all take the high word from `io_Actual`.
- Failure scenario: move or zero a partition whose start lies beyond 4 GB on a
  disk with a TD64 driver (or a Linux raw device). Every read and write lands
  at `offset mod 4 GB`: the copy reads the wrong source and overwrites data in
  the first 4 GB of the disk. The fuzz harness never exercises MOVE or disks
  over 1.2 GB, so this has no coverage.
- Fix: set `io_Actual = (ULONG)(byte_off >> 32)` (keep `iotd_Count` too for
  drivers that read that), mirroring `rdb.c`. Better: move the multi-block
  read/write into `rdb.c` as `BlockDev_ReadBlocks/WriteBlocks` so there is one
  TD64 implementation (see F-40).
- Confidence: confirmed by reading both call sites and the shim.

#### F-2 SFS bitmap helpers are endian-native (Linux build writes scrambled bitmaps)
- File: `src/sfsresize.c:153-170` (`sfs_bm_set_free/set_used/is_free`),
  `src/sfsresize.c:1085-1101` (`SFS_ShrinkInfo` bit scan), plus the `bm[]`
  writes at `src/sfsresize.c:562`, `635` and the gate at `1366-1380`
- Category: data-safety, portability
- What: bitmap words are accessed as `ULONG *` over a big-endian block. On the
  Amiga this is correct; on a little-endian host bit `31-k` of the loaded word
  is not block `base+k`. Everything else in the SFS engine goes through
  `sfs_getl/sfs_setl`, and the checksum is recomputed consistently, so nothing
  detects the damage.
- Failure scenario: `amipart IMAGE=... GROW DH0 ...` on Linux against an SFS
  partition. Reproduced: on identical images the m68k binary produced BTMP
  longword `0003FFFF` where the native binary produced `007F83FF` (512-byte
  case, sector 2, offset 12; several more blocks differ). The disk then has
  blocks marked used/free at the wrong positions; SFS can later allocate over
  its own end root or bitmap. Every SFS grow, shrink and SHRINKINFO run on
  Linux is affected. The fuzz passed 40/40 because `verify_sfs()` in
  `test/testloop.py:416-434` only checks the root blocks and the data hashes.
- Fix: replace the three helpers and the two scan loops with byte-addressed
  bit operations (`byte = 12 + bit_off/8; mask = 0x80 >> (bit_off%8)`) or
  `sfs_getl/sfs_setl`. Add a bitmap-content comparison to `verify_sfs()` and a
  CI step that runs one reference script on both binaries and `cmp`s the
  images (the experiment that found this).
- Confidence: confirmed experimentally.

### MAJOR

#### F-3 `BLOCKSIZE` in CLI/script creates physically overlapping partitions
- File: `src/cli.c:1252-1256`, `src/cli.c:1343-1344`, `src/script.c:695-700`,
  `src/script.c:762-763`; overlap check in cylinders only at
  `src/rdb.c:1522-1531`
- Category: data-safety
- What: `BLOCKSIZE=n` is stored as `pi->block_size = n` with
  `sectors_per_block = 1`, i.e. `DE_SIZEBLOCK = n/4`. AmigaOS handlers address
  a partition in units of `DE_SIZEBLOCK*4` bytes, so a partition declared at
  cylinders 10-20 with `BLOCKSIZE=1024` physically covers cylinders 20-41 of a
  512-byte-sector disk. AmiPart's own engines agree with that interpretation
  (`src/partmove.c:244-254`, `src/partclone.c:137-146`,
  `src/pfsresize.c:207-219` all scale the physical base by `block_size/512`),
  but `RDB_Write`, `RDB_IntegrityCheck`, the CLI clamp logic and the GUI map
  compare plain cylinder numbers.
- Failure scenario: `ADDPART NAME=DH0 LOW=10 HIGH=20 BLOCKSIZE=1024` followed by
  `ADDPART NAME=DH1 LOW=21 HIGH=40`: no overlap is reported, the RDB is
  written, and the two filesystems share cylinders 21-40.
- Fix: do what the GUI already does (`src/partview_dialogs.c:844-848`): keep
  `block_size = 512` and express larger FS blocks as `sectors_per_block`.
  Reject or convert `BLOCKSIZE>512` in CLI and script; make `RDB_Write` refuse
  `DE_SIZEBLOCK != 128` unless the geometry is scaled consistently. Update
  `cmdline.txt:439-442`.
- Confidence: confirmed by reading the write path and the engines' physical
  base math.

#### F-4 GUI FFS grow commits the filesystem but not the RDB
- File: `src/partview_move.c:855-901` (success path when the volume was
  unmounted), caller sets `dirty = TRUE` at `src/partview.c:2618`, `2836`,
  `3097`, `3385`
- Category: data-safety
- What: After `FFS_GrowPartition` succeeds the code remounts with the new
  geometry and returns; `RDB_Write` is left to the user. The PFS and SFS
  grows (`partview_move.c:972`, `1040`) and the shrink flow
  (`partview_move.c:1248`) write the RDB immediately, and the shrink comment
  explicitly calls the FFS deferral unsafe.
- Failure scenario: grow an FFS partition in the GUI, then press Back and
  choose Discard (or the machine loses power before Write). On disk the root
  has moved to the new centre and the root's children point at it
  (`ffsresize.c` phase 9b), while the RDB still has the old HighCyl. After a
  reboot FFS mounts with the old geometry, finds the old root, and lists it as
  empty. Data is intact but invisible until someone rewrites the RDB with the
  grown size.
- Fix: write the RDB right after a successful FFS grow (same as the other two
  engines), and make the Discard/Back prompt refuse to discard while a grown
  filesystem is pending.
- Confidence: confirmed by reading.

#### F-5 Progress callback type mismatch in partition clone (PR #9)
- File: `src/partclone.c:780-781`, `src/partclone.c:821-823`
- Category: crash
- What: `PartClone_PartToPart` forwards its `MoveProgressFn` (ud, done, total,
  phase) into `FFS_GrowPartition`/`SFS_GrowPartition`, which call an
  `FFS_ProgressFn` (ud, msg). The strict host build flags both sites with
  `-Wincompatible-pointer-types`; the Amiga build hides it with
  `-Wno-incompatible-pointer-types`.
- Failure scenario: clone an FFS or SFS partition into a larger destination
  (CLI `PARTCLONE`, script `PARTCLONE`, GUI Copy Partition). The engine calls
  the callback with two arguments; the CLI/GUI callback reads `done`, `total`
  and dereferences `phase` from stack garbage. On m68k that is a likely crash
  mid-clone.
- Fix: merge PR #9 (adapter struct). Remove `-Wno-incompatible-pointer-types`
  and `-Wno-int-conversion` from the Makefile so this class cannot return.
- Confidence: confirmed (compiler diagnostic plus reading both signatures).

#### F-6 Window-title buffers overflow with long image paths
- File: `src/partview.c:2043` with `2192-2194` (`win_title[80]`),
  `src/partview.c:1875-1879` (`t[96]` in `set_title_dirty`)
- Category: overflow (memory corruption)
- What: Both use unbounded `sprintf` of `"AmiPart V0.7" + " - %s unit %lu%s"`
  where `%s` is `devname`. For an image the caller passes `"FILE:" + path`
  (`src/main.c:509`, path up to 255 chars) and the dirty suffix is 34 chars.
  `t[96]` overflows once the device string exceeds about 35 characters, e.g.
  `FILE:Work:Emulation/Images/Disk.hdf`.
- Failure scenario: open a disk image from the GUI with a normal-length path,
  add a partition (title turns dirty): the static buffer overruns into
  neighbouring BSS.
- Fix: `snprintf(sizeof)` and truncate the device name with a `%.40s`
  precision (the formatter supports `%.Ns`).
- Confidence: confirmed by arithmetic on the actual format strings
  (`catalogs/AmiPart.cd:754-758`).

#### F-7 Overlapping partition move: failure after the copy leaves no valid table entry
- File: `src/partmove.c:347-357`, `374-378`, `407-414`
- Category: data-safety
- What: When the SFS root cannot be read, is not an SFS root, or its rewrite
  fails, `PART_Move` returns FALSE without updating `pi->low_cyl/high_cyl`.
  The block copy has already run. If the source and destination ranges overlap
  (a move by less than the partition length), the copy has by then destroyed
  part of the source.
- Failure scenario: move an SFS partition 50 cylinders down on a disk where the
  new end-root sector has a read error. Data now lives at the new location, the
  RDB still points at the old one (partially overwritten), and the comment at
  line 352 ("warn but don't fail the move") does not match the `goto`.
- Fix: read and validate the SFS roots before moving; after the copy, always
  commit `pi` to the new location and report metadata failures as warnings.
- Confidence: confirmed by reading.

#### F-8 RDB write failure after a successful grow/shrink is not handled
- File: `src/cli.c:1586-1589`, `src/cli.c:1865-1868`, `src/script.c:1797-1799`,
  `src/script.c:2020-2022`
- Category: data-safety
- What: The order is unmount, resize filesystem, write RDB. If `RDB_Write`
  fails (verify mismatch, overflow, I/O error) the code prints `FAILED` and
  returns. The filesystem is resized, the RDB is old, the partition is
  unmounted, and nothing tells the user what state the disk is in or what
  HighCyl to restore.
- Failure scenario: any `RDB_Write` failure after `FFS_GrowPartition`: after
  reboot the volume appears empty (see F-4 for why); after
  `SFS_GrowPartition` the volume will not mount (SFS requires an exact block
  count).
- Fix: retry once, then print the exact recovery (`the filesystem on X is now
  N cylinders; write an RDB with HighCyl=M`) and keep the volume inhibited.
  Longer term, a two-phase commit marker.
- Confidence: confirmed by reading.

#### F-9 Truncated PART/FSHD chains are silently accepted, then written back shorter
- File: `src/rdb.c:870-885` (PART checksum/read `break`), `902-910`,
  `1013-1022` (FSHD)
- Category: data-safety
- What: A read error or checksum mismatch in the middle of a chain ends the
  walk with no flag in `RDBInfo`. `RDB_IntegrityCheck` (`rdb.c:1272-1300`)
  iterates the in-memory list, so it cannot notice either.
- Failure scenario: one PART block develops a bad checksum; the GUI shows N-1
  partitions; the user edits something unrelated and clicks Write; the
  remaining partitions are dropped from the table.
- Fix: add `chain_truncated` (with the offending block) to `RDBInfo`, show a
  warning in GUI/CLI/script, and refuse `RDB_Write` unless forced.
- Confidence: confirmed by reading.

#### F-10 Raw Block Scan diagnostic overflows its line buffer when it finds differences
- File: `src/partview_rdb.c:1490-1508` (`MREAD_BLK` macro, `_ln[80]`),
  `src/partview_rdb.c:1586-1601`
- Category: overflow (stack)
- What: `"    R%d vs R1: %lu differ"` (about 24 chars) plus up to six
  `"  @%03lX:%02X->%02X"` entries of 13 chars each = up to 102 chars into an
  80-byte stack buffer.
- Failure scenario: five or more differing bytes between consecutive reads (the
  A3000 SDMAC shift case this tool exists for) smash the stack while the
  diagnostic runs.
- Fix: `snprintf` with remaining-space arithmetic; 160-byte buffer.
- Confidence: confirmed by arithmetic.

#### F-11 Linux `IMAGE=... CREATE SIZE=...` produces a 0-byte image
- File: `src/rdb.c:281-290` (`if (res != 0)` fallback), `host/amiga_shim.c:352`
  (`SetFileSize` stub returns 0)
- Category: correctness (host)
- What: `BlockDev_CreateFile` treats a non-zero `SetFileSize` return as failure.
  AmigaOS returns the new size on success (so the fallback seek+write always
  runs there, harmlessly). The host stub returns 0, which the code reads as
  success, and the file is never extended.
- Failure scenario: `./host/amipart IMAGE=t.hdf CREATE SIZE=8M INIT NEW` →
  reproduced: `t.hdf` is 0 bytes and INIT fails with "Cannot read disk
  geometry". Documented feature (`cmdline.txt:64-73`, README) is broken on
  Linux.
- Fix: test `res == -1`; implement `SetFileSize` in the shim with `ftruncate`.
- Confidence: confirmed experimentally.

### MEDIUM

#### F-12 `dol_Startup` treated as a BPTR without the `< 1024` guard
- File: `src/devices.c:209-216`, `src/quickformat.c:430-433`,
  `src/partview_rdb.c:1376-1379`
- Category: crash
- What: Handlers such as AUX:, SER:, PIPE: store a small integer in
  `dol_Startup`. `BADDR()` of that yields a pointer into low memory whose
  contents are then dereferenced as a `FileSysStartupMsg` and a BSTR.
- Failure scenario: `Devices_Scan` runs immediately after the startup warning
  (`main.c:491`). On a system with an MMU-protected zero page (Enforcer,
  MuForce, some 060 setups) this is an instant hit; on others it reads garbage
  device names. This matches the shape of GitHub issues #12 and #3 (instant
  crash after the warning requester on 3.2.x 060 systems).
- Fix: `if ((ULONG)startup < 1024) continue;` (HDToolBox's rule), and
  validate `fssm_Device` before reading its length byte.
- Confidence: likely.

#### F-13 GUI grow/shrink and DELPART unmount by DOS name only
- File: `src/partview_move.c:829`, `1207`, `src/partview.c:1937`,
  `src/cli.c:2597`, `src/script.c:2340`
- Category: data-safety
- What: `UnmountDevice(name)` matches the first DosList entry named e.g. `DH0`,
  regardless of device/unit. `quickformat.c:414-419` documents that this is
  unsafe and provides `UnmountPartition(bd, name)` (device+unit qualified),
  which the CLI/script GROW and SHRINK already use.
- Failure scenario: two disks both carrying a `DH0`; growing disk B's `DH0` in
  the GUI sends `ACTION_DIE` to disk A's handler and removes its DosList entry,
  then remounts disk B's partition under that name.
- Fix: use `UnmountPartition` everywhere; better still, match on
  `fssm_Environ` LowCyl/HighCyl so a partition mounted under a different name
  is also found (see F-14).
- Confidence: confirmed by reading.

#### F-14 Engines proceed on a live volume when `Inhibit` by RDB name fails
- File: `src/ffsresize.c:303`, `src/ffsresize.c:1520`, `src/sfsresize.c:330`,
  `src/pfsresize.c:567-572`; GUI PFS grow never unmounts
  (`src/partview_move.c:935-1005`)
- Category: data-safety
- What: The engines `Inhibit("<rdbname>:")` and treat FALSE as "not mounted".
  A partition mounted under another name (custom mountlist, or renamed in this
  session before writing) or a handler that refuses `ACTION_INHIBIT` is then
  modified live. `PFS_ShrinkInfo` and the PFS shrink gate read without
  inhibit by design (`pfsresize.c:786`, `1088`), and `PFS_GrowPartition`
  writes the rootblock before inhibiting (`pfsresize.c:533-572`), so a handler
  flush in that window can overwrite the new rootblock.
- Failure scenario: GUI Edit → grow of a mounted PFS3 partition: no unmount is
  attempted at all; the rootblock is rewritten under a live handler; if the
  handler flushes its cached rootblock afterwards the SIZEFIELD clear is lost
  and the volume reports "Uninitialized" after reboot.
- Fix: callers must guarantee the volume is offline (DosList lookup by
  device+unit+LowCyl); engines should refuse when the volume is found mounted
  and `Inhibit` fails. `offer_pfs_grow`/`offer_sfs_grow` should go through the
  same unmount path as the FFS grow.
- Confidence: confirmed by reading (race window is real; frequency unknown).

#### F-15 `RDB_Write` writes the RDSK first
- File: `src/rdb.c:1627-1640`
- Category: data-safety
- What: Blocks are written in ascending order, so the RDSK (which points at the
  new PART/FSHD/LSEG blocks) hits the disk before those blocks exist.
- Failure scenario: power loss or driver error after block 0 and before the
  PART blocks: the disk has a valid new RDSK pointing at stale or half-written
  chain blocks.
- Fix: write `rdb_block_lo+1 .. last` first, RDSK last, then verify.
- Confidence: confirmed by reading.

#### F-16 Stale RDSK left behind when `block_num != rdb_block_lo`
- File: `src/rdb.c:1571`
- Category: data-safety
- What: The RDSK is always written at `rdb_block_lo`. If the RDSK was found at a
  lower block (e.g. found at 0 with `RDBBlocksLo = 1`), the old RDSK at block 0
  survives and wins the ROM's 0..15 scan.
- Failure scenario: the write "succeeds" but the machine keeps booting the old
  table.
- Fix: after writing, zero every other block in 0..15 that carries an RDSK ID.
- Confidence: likely (depends on foreign-tool layouts).

#### F-17 RESTORE writes the saved RDSK to block 0 unconditionally
- File: `src/cli.c:1037`, `src/script.c:1168`, `src/partview_rdb.c:311`
- Category: data-safety
- What: BACKUP saves `rdb->block_num`; RESTORE always writes block 0.
- Failure scenario: MBR+RDB disk (RDSK at block 1): restore destroys the MBR
  and leaves an RDSK at 0 whose `RDBBlocksLo` says 1.
- Fix: write to `rdb_RDBBlocksLo` read from the saved block, or steer users to
  ERDB (which carries `block_lo`).
- Confidence: confirmed by reading.

#### F-18 BACKUPEXT trusts `rdb_HighRDSKBlock`
- File: `src/cli.c:1086-1088`, `src/script.c:1218-1220`,
  `src/partview_rdb.c:378-381`
- Category: data-safety
- What: When the field is 0 or `0xFFFFFFFF` (some tools never set it) the
  backup contains only the RDSK block.
- Failure scenario: RESTOREEXT of such a backup restores an RDSK whose chains
  point at blocks that may have changed since.
- Fix: compute the extent from the parsed PART/FSHD/LSEG chains and use the
  maximum of the two.
- Confidence: confirmed by reading.

#### F-19 RESTOREEXT does not check that the backup belongs to this disk
- File: `src/cli.c:1161-1184`, `src/script.c:1286-1313`,
  `src/partview_rdb.c:556-584`
- Category: data-safety
- What: Only magic, version, block size and file size are validated.
- Fix: compare the backup RDSK's cylinders/heads/sectors and product string with
  the target and require FORCE on mismatch.
- Confidence: confirmed by reading.

#### F-20 Filesystem manager: Cancel keeps deletes/edits but reports "no changes"; delete relabels partitions
- File: `src/partview_fs.c:679-690`, `src/partview_fs.c:790-793`
- Category: correctness, data-safety
- What: Cancel only rolls back additions; deletes and edits stay in `rdb` with
  `dirty = FALSE`, so Back exits without the unsaved warning and a later Write
  commits them. Deleting a driver also rewrites every partition of that dostype
  to `DOS\1`.
- Failure scenario: delete the PFS3 entry by mistake, press Cancel, later
  Write for another reason: PFS3 partitions are now labelled FFS in the RDB.
- Fix: snapshot `filesystems[]`/`num_fs` on entry and restore on Cancel; refuse
  to delete a driver that partitions still use (or leave their dostype alone).
- Confidence: confirmed by reading.

#### F-21 BADB chain written by Bad Block Scan is dropped by the next Write
- File: `src/partview_rdb.c:2960-3024`, `src/rdb.c:1580`
- Category: correctness
- What: `write_badb` patches `rdb_BadBlockList` on disk; `RDB_Write`

- Confidence: confirmed by reading.

#### F-22 Clone into a larger partition passes the wrong block count for 1024-byte FFS

#### F-27 Image files are capped at 2 GB on Linux too
- File: `src/rdb.c:588-594`, `645-648` (`LONG off`), `host/amiga_shim.c:342-351`
- Category: portability, performance
- What: The `BD_FILE` path uses `LONG` seeks. That is a real AmigaOS limit but
  an artificial one on the host, where 4 GB and larger HDFs are common.
- Fix: on the host, give `BD_FILE` a 64-bit `pread/pwrite` path (`UQUAD`

- Confidence: confirmed by reading.

#### F-28 FFS grow diagnostic and other engine messages use unbounded `sprintf` into fixed buffers
- File: `src/ffsresize.c:1063-1077` (`MSG_FFS_SUCCESS_DIAG`, 13 numbers into a

- Category: overflow
- What: The engines never learn the caller's buffer size (`errbuf[256]` in the
  GUI, `outbuf[400]` in the CLI, `s_msg[400]` in scripts). With translated
  catalogs or 10-digit block numbers the 256-byte GUI buffers are exceeded.
- Fix: pass `ebsz` to the engines (as `partclone.c` already does) and use
  `snprintf`.
- Confidence: likely (English strings fit today with a small margin).

#### F-29 UTF-8 bytes in the catalog
